# Decisions

This is the record of choices that are already locked in for this project.
If a decision changes later, it gets added here (with the date) instead of
just being changed silently — so there's always a paper trail of "why is it
built this way."

- **Framework:** Next.js, using the App Router.
- **Language:** JavaScript — not TypeScript (kept simple, no type-checking layer).
- **Styling:** Tailwind CSS.
- **Database + admin login:** Firebase (to be connected in Step 5).
- **Hosting:** Vercel (to be set up in Step 8).
- **Brand name:** "Navavia" (tagline: "Where Ideas Take Form") — used across the homepage, header, and browser tab title.
- **Each project page shows:** a live link to the project, customer-facing screenshots, and admin-panel screenshots — all three, clearly separated.
- **Code style:** one function/component per file, with a plain-English comment at the top of every file explaining what it does and when it runs.
- **2026-09-12 — Project walkthrough videos:** hosted on YouTube as unlisted videos and embedded on the project detail pages, not uploaded directly to the site.
- **2026-09-12 — Geographic scope:** the business serves clients worldwide, not only locally. No city or region name should appear in site copy, headlines, or taglines.
- **2026-09-12 — Client reviews:** added by the admin only. Visitors cannot submit reviews on this site.
- **2026-09-12 — Admin login method:** Firebase Authentication with email + password. The admin account itself is created manually in the Firebase Console (Authentication → Users), not through the app — this app only checks sign-in, it doesn't create new admin accounts.
- **2026-09-12 — Database security rules:** anyone can read projects/reviews (so the public site works for visitors); only a signed-in admin can create, update, or delete them. Everything else is denied by default. Defined in `firestore.rules`, but only takes effect once published in the Firebase Console's Rules tab — the file alone does nothing.
- **2026-09-12 — How public pages load data:** the homepage, projects page, project detail pages, and reviews page all fetch from Firestore in the browser (not on the server) so each one can show a loading message, then either the real content or a clean error message if the database is unreachable — never a blank page or a crash. Trade-off: content isn't present in the page's initial HTML, which matters for search-engine visibility — worth revisiting when Step 8 (the SEO-focused blog) or Step 11 (deploy) come up.
- **2026-09-12 — Public site and admin panel are structurally separate:** public pages live under `app/(site)/` with their own layout (Header/Footer); the admin area lives entirely under `app/admin/` with its own sidebar layout. The root layout adds neither — this is what guarantees the public header/footer can never leak into the admin panel, or vice versa.
- **2026-09-12 — Image storage: Cloudinary, not Firebase Storage.** Firebase Storage now requires a paid ("Blaze") plan, so uploaded screenshots and client photos are hosted on Cloudinary's free plan instead, inside a "seller-backbone" folder (never the root). Firestore (the database) and Authentication (admin login) are unaffected and remain on Firebase's free "Spark" plan exactly as before. Uploads use an unsigned upload preset (no secret key exposed to the browser), and every image link is automatically served compressed and in a modern format (via Cloudinary's f_auto,q_auto).
- **2026-09-12 — Deleted images are not removed from Cloudinary automatically.** Cloudinary's free plan doesn't support deleting files from the browser side (that needs a secret key this app never exposes). Deleting a project or review, or removing a single image in a form, only removes its link from the database — the admin Dashboard has a note reminding you to clear unused files from the Cloudinary website directly if storage ever fills up.
- **2026-09-13 — Contact form spam protection is client-side only (localStorage), not a server-side limit.** The same browser can't submit more than 3 enquiries per hour — enforced by checking timestamps saved in that browser's own storage, not on Firebase's side. This is a deterrent against casual repeat submissions, not a hard security guarantee — someone could clear their browser data or use a different browser/device to get around it. Revisit if spam becomes a real problem (e.g. with a server-side check, or a CAPTCHA).
- **2026-09-13 — Enquiry status workflow:** New → Contacted → In Discussion → Won / Lost, set manually by the admin from the enquiries dashboard. Every new enquiry starts as "New" automatically; nothing else changes its status without the admin doing so.
- **2026-09-13 — Two separate kinds of video, two separate places:** per-project walkthrough videos (`youtubeId` on a project) live on that project's own detail page; general "About Our Business" videos (the `homepageVideos` collection) live in the homepage's "How We Work" section. They're unrelated and managed in different parts of the admin panel on purpose, since they serve different audiences (someone looking at one specific project vs. a first-time visitor).
- **2026-09-13 — Business renamed from Seller Backbone to Navavia**, tagline "Where Ideas Take Form." Every visible mention of the old name across the site, admin panel, and docs was updated. Internal service identifiers (the Firebase project id, the Cloudinary cloud name, the Cloudinary upload preset name, and the Cloudinary folder where images already live) were deliberately left unchanged — renaming any of those would have broken the live site rather than just changed a label.
- **2026-09-13 — Blog pages load data on the server, unlike the rest of the public site.** Every other public page (homepage, projects, reviews, contact) fetches from Firestore in the browser (see the 2026-09-12 decision above) for clean loading/error states. The blog is the deliberate exception: `app/(site)/blog/page.js` and `app/(site)/blog/[slug]/page.js` fetch on the server so each post can have its own real page title, description, and social-share preview image — the entire point of building a blog for SEO. This is also what makes `generateMetadata` and the sitemap possible.
- **2026-09-13 — A draft blog post is only viewable by the signed-in admin, never via a shareable public link.** Enforced in `firestore.rules` (`resource.data.published == true || request.auth != null`), not just in the app. The admin's "Preview" button works around this by living at `/admin/blog-preview/[postId]` — a page outside both the public layout and the admin sidebar, so it looks exactly like the real post, but reads the post using the signed-in browser's own permissions. If you're not signed in (or the post doesn't exist), it shows "Post not found," same as a random visitor would see.
- **2026-09-13 — Blog post content is rich text (HTML) from a WYSIWYG editor (TipTap), not Markdown.** Chosen so the admin never needs to know any syntax — just buttons (Bold, headings, lists, links), same as a word processor. The saved HTML is rendered with a hand-written `.blog-content` CSS class in `app/globals.css` rather than the Tailwind Typography plugin, to avoid adding a new build-time dependency for something a few CSS rules already cover.
- **2026-09-13 — Reading time and the slug are both automatic, not admin-typed.** Reading time is recalculated from the content every time a post is saved (roughly 200 words per minute, minimum 1 minute) and is never directly editable. The slug is generated from the title as the admin types, but can be overridden — attempting to save a slug already used by a different post is blocked with a clear warning rather than silently creating a URL collision.
- **2026-09-13 — Firestore rules lesson: when a rule depends on a field, every search on that collection must include that field in the search itself, or Firestore blocks it.** Learned from the "Post not found" bug: a *get-this-exact-item-by-id* request is checked against the document's real data, but a *search* (any `where()` query, even one that can only ever match one document) is checked against the shape of the search itself, before Firestore looks at any data. If a rule says "allowed if field X is true, or you're signed in," a signed-out search that never mentions field X can't be proven safe in advance, and gets refused outright — even when the one document it would have found genuinely has X set to true. The fix is always the same: add that field to the search's own `where()` clauses; don't rely on checking it only after the data comes back. Relevant any time a new collection's rule branches on one of its own fields.
- **2026-09-13 — Per-page SEO titles never get the brand name appended automatically if the admin already typed one.** On the blog post page, a custom "SEO Title" is used exactly as typed; "— Navavia" is only added automatically when that field is left blank. This applies to the browser tab title and the social-share preview title alike. Checked and confirmed this kind of duplication has no equivalent on the projects, reviews, or contact pages — none of those have a per-item editable title field, so there was nothing to double up.
- **2026-09-13 — Site URL comes from `NEXT_PUBLIC_SITE_URL`, falling back to `http://localhost:3000`.** Used by the sitemap, robots file, blog post canonical links, and the homepage's social-share image. Not set anywhere yet since the site isn't live on a real domain — this is the environment variable to add in Vercel during Step 11 (deploy), set to the real `https://...vercel.app` address once known.
- **2026-09-13 — The homepage's social-share preview image is generated by code (`app/opengraph-image.js`), not a saved image file.** Next.js builds a branded image (dark background, "Navavia" + tagline) on the fly using its built-in image-generation feature, rather than a designed graphic uploaded somewhere — quick to set up now, easy to replace with a real designed image later by editing that one file.
- **2026-09-13 — Data-loading pattern in admin list pages: a `.then()` chain, not an `async`/`await` function, inside `useEffect`.** A newer ESLint rule (`react-hooks/set-state-in-effect`, part of `eslint-config-next`) flags the `async function` + `await` version of "fetch on mount, then setState" as looking like an unsafe synchronous state update, even though it isn't. Rewriting the same logic as `somePromise.then(result => setState(...))` satisfies the rule and behaves identically — this is now the standard pattern for that shape of code in this project. Confirmed by testing both versions directly against the linter.
- **2026-09-13 — `not-found.js` lives at the project's top level, not alongside the other public pages, and includes the Header/Footer itself.** Only a top-level `not-found.js` catches a URL that doesn't match anything at all (one placed inside `app/(site)/` only catches an explicit `notFound()` call from within that section). Since it can't inherit the public layout from there, it imports Header and Footer directly instead, so a broken link still looks and feels like the rest of the site.
- **2026-09-13 — `lib/firebase.js` sets up the database (`db`) immediately, but Authentication only lazily, via `getFirebaseAuth()`.** Reason: importing this file used to always call `getAuth()` and `setPersistence()` (browser-only sign-in setup) as an automatic side effect, regardless of what was actually needed. That's harmless in a browser, but pages that only read the database and run on Vercel's build servers — the sitemap, and the blog pages — imported this file too (indirectly, through `lib/firestore.js`), and paid the cost of that unrelated Authentication setup running somewhere it was never designed for, which surfaced as a confusing `auth/invalid-api-key` crash that took down the whole deployment. Now, reading the database never touches Authentication in any way, and every file that actually needs to sign in or check sign-in status (the admin login page, the admin sidebar, the public footer's admin link) calls `getFirebaseAuth()` instead of importing a ready-made `auth` value. Confirmed by rebuilding the site locally with a genuinely invalid API key and a genuinely non-existent Firebase project — both builds succeeded, with the sitemap correctly falling back to just its fixed pages (homepage, projects, reviews, blog, contact) when the database truly couldn't be reached.
- **2026-09-13 — The sitemap now includes every individual project page, not just the "/projects" listing.** Matches how blog posts are already included — each project's own page joins the sitemap automatically. Every part of the sitemap that reads the database is wrapped in its own try/catch, on top of `lib/firestore.js`'s own error handling, so nothing about the database can ever fail the sitemap's build — only reduce what it's able to list that time.
- **2026-09-13 — The Services page (`/services`) has no database behind it at all.** Every word is written directly into `app/(site)/services/page.js` as fixed content — there's nothing to fetch and nothing that can fail to load. To change the wording later, edit that file directly.
- **2026-09-13 — A social-share preview image (`opengraph-image.js`) only applies to the exact page it's placed next to — it doesn't automatically cover other pages.** Confirmed directly: the homepage's `app/opengraph-image.js` did not apply to `/services`, so `/services` needed and got its own `app/(site)/services/opengraph-image.js`. Worth remembering for any future page that needs to look right when shared on WhatsApp/LinkedIn — it needs its own image file (or an explicit `openGraph.images` entry in its metadata, as the blog posts already do using each post's cover image) rather than assuming it inherits one from elsewhere.
- **2026-09-13 — Every single database read and write goes through a 15-second timeout, via `runWithTimeout()` in `lib/firestore.js`.** Firebase's own library has no built-in "give up after a while" — left alone, if a visitor's connection can't complete the handshake with Google's servers for any reason, the request just waits forever with no error and nothing on screen explaining why. This is exactly what happened on the live homepage: it starts three database reads together and waits for all three, so one silently-hung read left the whole page stuck on "Loading our work..." permanently. Every function in `lib/firestore.js` is now guaranteed to settle — successfully or with a clear "took too long" message — within 15 seconds, no exceptions, so no page anywhere in the app can be left loading forever again. Proved this works (not just assumed) by testing the exact same timeout logic against a promise that deliberately never resolves — it was correctly given up on at exactly the configured time, every time.
- **2026-09-13 — Fixed a real security hole: self-signup made "signed in" meaningless.** You reported admin pages opening without a password. Investigating found the admin page-protection code itself was fine — every admin page is inside `app/admin/(panel)/layout.js`, which never renders any admin content until Firebase confirms a real signed-in user, and there's no dev-only shortcut anywhere. The real hole was one level deeper: Firebase's own "Email/Password" sign-in method, by default, lets *anyone* create their own brand-new account through the public API — proved this directly by creating (then deleting) a throwaway account using nothing but the site's own public API key, the same key that's already visible to anyone in the browser. Since the security rules only ever checked "is someone signed in?" rather than "is this specifically the admin," a stranger could self-register and then pass that check — for the admin panel's own login form, and for every Firestore rule guarding real data. You chose not to hardcode one specific email into the rules (so you can freely add or remove admin accounts from the Firebase Console without ever touching code) — instead, the fix is to turn off self-signup in the Firebase Console (Authentication → Settings → User actions → "Enable create (sign-up)" OFF) so the only accounts that can ever exist are ones you create yourself there. Checked anonymous sign-in too (a separate, even easier hole in some projects) — confirmed it's already disabled on this project. Also checked the current database contents for any sign of tampering during the time this was open — found none; the only projects/reviews/homepage videos present are the original starter/seed data.
- **2026-09-13 — The public footer's admin link no longer depends on being signed in, and always points to /admin/login.** Previously, the footer only showed an "Admin Panel" shortcut to `/admin` when the visitor's browser happened to already be signed in — meaning a signed-out admin, on a fresh browser, had no footer link at all, and the one visible only ever skipped straight past the login form. Now the footer always shows (or hides, per the new setting below) a plain "Admin Login" link to `/admin/login` itself, regardless of sign-in state — clicking it always lands on the real form and always requires typing the email and password; nothing about this link can ever sign someone in automatically.
- **2026-09-13 — Added a `settings` collection in Firestore and a new admin "Settings" page**, currently holding one switch: "Show admin login link in footer" (default on). Anyone can read it (the public footer needs to check it to decide whether to render its link), but only a signed-in admin can change it. This is the first "site-wide switch you can flip without a code change" — a natural place for more of these later.
- **2026-09-13 — Every public page is now built from admin-editable "sections" stored in a new `pageContent` collection**, managed from a new admin "Pages" screen (Home, Services, Projects, Reviews, Blog, Contact). Each section has a type (Heading, Text Block, List of Points, Image + Text, Set of Cards, Quote/Highlight, Call to Action, or one of five "automatic" types), a heading/subheading, and — depending on type — body text, an image, a button, or a list of items. Anyone can read sections; only a signed-in admin can add, edit, delete, or reorder them (`firestore.rules`).
- **2026-09-13 — No separate About page was built.** Item 9 of the original request asked for one, sourced from the Services page's "What Makes Us Different" section — but when asked to confirm that specific content, the answer was that Services works fine as one page and a separate About page isn't needed. Services keeps all of its existing content, including that section, as one page with 9 editable sections.
- **2026-09-13 — The Hero (homepage headline) and the "Ready to get started?" closing section are deliberately NOT part of the section system — they stay fixed in `components/Hero.js` and `components/ClosingCTA.js`, exactly as they already were.** Reason: the section schema supports exactly one optional button per section, but Hero has two ("View Our Work" and "Get in Touch") and ClosingCTA has a button plus two extra fixed contact links (email, WhatsApp) below it. Forcing either into the generic schema would have meant either quietly dropping a button/link that was never asked to be removed, or changing how every other "cta"-type section looks site-wide to accommodate extra links only these two needed. Kept both exactly as they were instead. If editable headlines/buttons on these two are wanted later, the schema would need a deliberate extension (e.g. a second button) — a decision for the admin to make, not one to default into silently.
- **2026-09-13 — On the Contact page, only the top heading/subheading became an editable section — the Email/LinkedIn info box beside the form stays fixed in code, not moved into the section system.** That box is three short, tightly-coupled lines (an email address, a LinkedIn link, one sentence) sitting inside the form's two-column layout, not a stackable "section" — and it's already known, separately-tracked placeholder content (see the 2026-09-13 full-site-audit entries below) waiting on real contact details, not general wording. The actual form (fields, validation, sending the enquiry) was already agreed to stay as code, unchanged.
- **2026-09-13 — Contact details (email, phone, WhatsApp, 8 social platforms) live in one place — the admin "Contact & Social" page — and every other place that shows them (footer, Contact page, homepage closing section) reads from there.** Replaces the `you@example.com`, `#` LinkedIn, and `00000000000` WhatsApp placeholders flagged in the earlier full-site audit. Each social platform has its own on/off switch and only shows an icon when a URL is actually entered AND turned on. The WhatsApp number is typed as digits-with-country-code only (e.g. `919876543210`) and a real `https://wa.me/...` link is built from it automatically — same idea as how a YouTube link is turned into just its video id elsewhere in this project.
- **2026-09-13 — Added `react-icons` as a new dependency, for the 8 social platform logos.** This project had avoided adding icon/UI libraries before (e.g. skipped Tailwind Typography for the blog) to keep dependencies minimal — asked directly this time whether to hand-code simple SVGs instead, and the answer was to install a proper library, so `react-icons` (`fa6` / Font Awesome 6 icon set) was added instead of hand-drawn icons.
- **2026-09-13 — The homepage enquiry form and the Contact page's form are the exact same component (`components/EnquiryForm.js`), not two copies.** Extracted from the Contact page so both places always behave identically and can never drift apart. One small behavior change from before: submitting successfully now shows a "Thanks for getting in touch" message in place of just the form fields, rather than replacing the Contact page's entire heading and info box — done so the same component works sensibly both on its own (Contact page) and embedded inside the homepage's closing section, where replacing the whole section would look wrong.
- **2026-09-13 — Settings toggles for Featured Work, How We Work videos, and Client Reviews only affect the homepage.** These three already had their own per-section "visible" switch in the admin Pages editor (Home → Sections); the new Settings-page switches are an additional, quicker on/off layer specifically for the homepage versions — a section only shows if BOTH switches allow it. The dedicated `/reviews` page's own reviews section is intentionally a separate, unaffected control — confirmed directly rather than assumed, since Reviews is the one case with both a homepage teaser and its own full page.
- **2026-09-13 — No toggle was built for "the about page."** It was on the original list for this update, but there is no About page — Services was confirmed (last session) to cover that content as one page. Flagged directly rather than silently building a toggle for a page that doesn't exist, or silently building the page itself.
- **2026-09-13 — Turning off the entire Blog or Services page removes it from navigation, search engines (the sitemap), AND shows the site's normal "Page Not Found" screen if the exact URL is opened directly** — chosen deliberately over a softer "temporarily unavailable" message, to match "disappears from the public site completely" as literally as possible.
- **2026-09-13 — Project screenshots changed shape: from a plain list of image links to a list of `{ url, caption }` pairs.** Every place that reads screenshots (the project detail page's gallery, and the homepage/projects-grid card thumbnail) accepts either the old plain-string format or the new object format, so nothing already saved ever breaks — old entries just show with an empty caption until edited and re-saved. Caught and fixed one real bug this change would have caused: `ProjectCard.js` used the first screenshot directly as an `<img>` source, which would have broken once that value became an object instead of a string.
- **2026-09-13 — The Customer/Admin screenshot uploader supports selecting or dragging several files at once, each uploading and reporting progress independently.** One failing (wrong file type, too large, a network hiccup) never stops or delays the others — proved this directly with a real test: three files uploaded to Cloudinary at the same time, one deliberately invalid, and the other two completed successfully regardless. The existing "paste an image URL" option (from before this change) was kept alongside the new multi-file picker, since it wasn't asked to be removed.
- **2026-09-13 — The screenshot popup's "don't scroll the page behind it" and "arrow keys" logic live in two separate effects, not one.** Combining them caused a real bug during review: re-running a single combined effect on every next/previous click would capture "hidden" as the "previous" scroll state partway through browsing, so closing the popup could leave the page stuck unable to scroll. Splitting them (scroll-lock only reacts to open/closed; arrow keys react to which image is showing) fixed it before it ever shipped.
- **2026-09-13 — No browser automation tool is available in this environment**, so the drag-and-drop, swipe gestures, and on-screen arrow/keyboard navigation for this update could not be clicked through in an actual browser before reporting done — verified everything else possible instead (a clean rebuild, a real concurrent-upload test against Cloudinary proving the partial-failure behavior, and close reading of the interaction code, which is how the two bugs above were caught). Said so directly rather than claiming a browser test that didn't happen — full step-by-step manual testing instructions were given instead.
- **2026-09-13 — Starter content for the new Pages system has to be imported by clicking a button in the admin panel, not automatically.** Same reasoning as every other one-time data import in this project (starter projects/reviews, starter homepage videos): writing to Firestore requires being signed in as the real admin, which this build process deliberately never has access to — see the 2026-09-13 security-fix entries above. `lib/firestore.js`'s `seedPageContent()` copies every page's real, existing wording (from `data/pageContentSeed.js`) into the database, once, the same way the other "Import Starter ___" buttons already work.
- **2026-09-13 — Added a temporary, unlinked `/debug` diagnostic page for tracking down live-only Firebase problems.** It shows, in plain text, which of the 10 `NEXT_PUBLIC_...` environment variables are present on whichever environment it's opened in (never their values), whether Firebase itself started up (with the exact error if not), and a live read attempt against each of the four public collections with timing and item counts. Needs no login by design — the point is to diagnose a broken live site, which by definition might not have working sign-in either — but it's excluded from search engines (`app/debug/layout.js` sets `robots: noindex`, and `/debug` is disallowed in `app/robots.js`) and never linked from anywhere in the site's navigation. It is meant to be deleted (the whole `app/debug` folder) once the underlying problem is fixed, not kept as a permanent feature. To make Firebase's exact startup error visible on this page, `lib/firebase.js` now also exports `firebaseInitError` — previously that error only ever reached the browser console.
